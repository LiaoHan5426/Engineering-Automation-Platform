# 专家工作流与手动重启检查

## 使用路径

1. 在数据库资料中登记脱敏表结构、字段类型和索引前导列，不保存密码、Token 或 JDBC 地址，不连接业务数据库。
2. 创建知识库，录入脱敏业务规则和已验证案例。
3. 复制内置专家，选择能力节点并建立依赖连线。能力目录按种类分为四个子页——总览 / 内置命令 / 本地 CLI / MCP 工具——每个子页都标注当前是否可用（本地 CLI 缺少可执行文件时显示「缺少可执行文件」，被平台停用时显示「已停用」）。节点名称和数组位置不决定执行顺序。
4. 选择知识库和数据库资料，校验并保存草稿。校验同时检查：若引用了规则包，流程中必须存在产出该规则包所需事实的能力节点，否则保存与启用都会被拒绝——这类缺失会让规则永远不命中，且看起来像「没有问题」。
5. 显式启用并授权。草稿引用不等于读取授权；保存新修改会停用专家并撤销旧授权。MCP 工具同样在这一步授权并同样在停用时撤销。
6. 在 SQL 工作台选择已启用专家，提供问题、SQL，以及可选的资料和 EXPLAIN JSON 快照。
7. 检查建议、知识引用和逐节点结果。必需节点失败会阻止依赖节点；缺少可选上下文返回部分分析，不伪装完成。规则依赖的能力本次未执行时，对应规则列在「未判定的规则」中并给出缺失的事实与能力，状态为部分完成——未判定不等于通过。

## 能力目录：每类能力都能管，但不能凭空造

只读目录只是半个目录。每一类能力都在后端声明自己能改什么（`CapabilityManagement`），控制台据此生成子页，而不是前端硬编码一个列表：

| 种类 | 管理入口 | 可以改 | 仍然是代码 |
|---|---|---|---|
| 内置命令 | 设置 | 启用/停用、备注 | 处理器本身：一个能力 = 一个 `CapabilityHandler` 组件 + 一条声明 |
| 本地 CLI | CLI 通道 | 启用/停用、备注、二进制位置、主动探测 | 命令与参数数组、产出的事实 |
| MCP 工具 | 服务器登记表 | 登记/修改/启用/信任/工具白名单/删除、探测 | 真正说协议的那段客户端 |
| HTTP 服务 | 暂无 | 目前无 | 端点、白名单与响应映射 |

三条性质让这个开关是诚实的：

- **缺省即启用。** `eap.capability_setting` 是选择退出，与信任表（缺省拒绝）相反；登记表不可读时平台照常可用，而不是整体瘫痪。
- **在用就不能关。** 停用一个「已启用专家」正在使用的能力会被拒绝，并列出仍在使用的专家名；只有草稿引用不阻止停用——草稿还不算平台的一部分。
- **停用不等于缺失。** 引用已停用能力的专家清单会被拒绝，提示「能力 X 已在平台停用……请在能力目录中重新启用」，绝不会说成「未实现的能力」；运行期解析也会再次拒绝，避免旧授权把它偷偷放回来。

本地 CLI 的覆盖是**即时生效**的（处理器持有按执行解析的 `Supplier`），改二进制位置不需要重启。页面渲染时不执行任何二进制——解析路径只查 `PATH`；只有点「探测」才会以 `<binary> --version` 运行一次，短超时、输出脱敏并截断。

**任何种类都不提供「新增能力」。** 新增能力需要改代码：一个 `CapabilityHandler` 组件加一条声明。控制台在总览页把这件事写明，而不是放一个点了也没用的按钮。

当前知识检索使用 PostgreSQL 全文检索和本地关键词（含中文二元切分），不是向量检索或通用语言理解。SQL 分析基于 AST，并将实际关联列与显式授权的结构、索引快照比较。快照不是实时数据库或平台实测的查询性能。

## MCP 工具：为什么不能全局启用

MCP 服务器为每个连接保留状态：会话标识、游标、协商结果，以及开启连接时的认证身份。如果平台像注册 `sql.parse` 那样把 MCP 工具「注册给所有专家」，两个专家就会共用同一会话——B 的调用可能落在 A 的状态与授权上下文里，A 留下的半消费游标会让 B 漏读，审计也无法区分发起人。因此这不是使用注意事项，而是结构性隔离：

1. **平台登记**：通过 `/api/mcp-servers` 登记服务器（能力目录的 MCP 工具页）。默认不启用、不信任，且带工具白名单。只有同时启用并信任的服务器才发布能力；登记表不可读时按「没有任何工具」处理，而不是「全部允许」。登记时就在源头校验：服务器 id 与工具名必须符合 `mcp.<服务器>.<工具>` 的分段形状（否则会造出一个任何专家都引用不到的能力 id），传输只允许 `stdio`/`http`/`sse`，端点里带凭据一律拒绝。
2. **能力命名**：`mcp.<服务器>.<工具>`，按服务器加前缀，两个服务器可以发布同名工具而互不覆盖。
3. **专家授权**：工具必须写进专家清单的 `mcpTools`，启用时写入 `eap.expert_mcp_grant`，停用时随其他授权一起撤销。流程中使用了未声明的专家级能力，保存与启用都会被拒绝。
4. **运行期解析**：即使处理器已注册，只有声明过该工具的专家才能解析到它；其他专家的该节点会以「专家级能力未在本专家清单中授权」失败，而不是静默调用。
5. **会话隔离**：一次调用只能使用属于 `(执行, 专家, 服务器)` 三元组的会话；执行之外、或冒用其他专家的会话都会被拒绝；执行结束（含失败）时统一关闭。

信任与启用独立于专家授权：一个服务器可以被登记、被信任，却仍没有任何专家引用；反过来，只要还有**已启用**专家持有它某个工具的授权，删除该服务器就会被拒绝。

当前尚未实现 MCP 客户端，因此空库下确实没有任何 MCP 工具：能力目录显示 0 项。但登记入口是存在的——它正是让这个页面「从空到有」的那一步，探测也会如实报告 `verified: false`，而不是假装已验证。

默认不调用模型，也不执行输入或模型生成的 SQL。模型增强需逐次选择；远端模型还需设置 EAP_LLM_ALLOW_REMOTE=true，并使用 HTTPS。模型文本始终是待验证观察，不能把部分流程变成已接受的完成状态。

## 接口

- GET /api/experts：定义、启用状态与版本。
- GET /api/capabilities：能力目录，按种类与权限范围（平台级 / 专家级）分组，含描述、输入、授权、执行者、产出事实、可用状态、管理入口、启用/停用与备注、MCP 服务器及被哪些专家引用。
- PUT /api/capabilities/{name}/activation：按能力启停（含备注）；有已启用专家正在使用则拒绝。
- PUT /api/capabilities/{name}/cli：覆盖本地 CLI 的二进制位置，即时生效。
- POST /api/capabilities/{name}/cli/probe：以 `<binary> --version` 主动探测，输出脱敏截断。
- GET/POST /api/mcp-servers、PUT/DELETE /api/mcp-servers/{id}：登记、修改、启用/信任与删除 MCP 服务器；有已启用专家持有其工具授权时拒绝删除。
- POST /api/mcp-servers/{id}/probe：探测服务器可达性；无协议客户端，报 `verified: false`。
- GET /api/experts/catalog：运行时实际支持的编排能力、规则与事实词汇，以及专家级能力词表、已登记的 MCP 服务器与平台停用能力清单。
- GET /api/rule-packs：规则包目录，含每条规则包声明的所需能力（requires）。
- POST /api/rule-packs/validate：在不保存的情况下校验规则包，包括 requires.capabilities 声明是否完整。
- POST /api/rule-packs/dry-run：对真实 SQL 试跑规则包，返回事实、结论、声明与推导出的能力需求，以及未判定的规则。
- POST /api/experts/validate：服务端独立检查图结构、引用、规则，以及规则包所需能力是否都有对应节点。
- POST /api/experts：保存停用的草稿。
- PUT /api/experts/{id}/activation：显式启用、授权或停用、撤销授权。
- POST /api/experts/{id}/execute：执行 DAG 并持久化观察。
- POST /api/sql/analyze：使用相同执行器，自定义 expertId 必须已启用。
- GET /api/tasks/{id}：读取完整任务证据。
- GET/POST /api/databases、GET/PUT/DELETE /api/databases/{id}：维护脱敏资料。当仍被已启用专家的清单声明时，删除返回 409 并点名专家；草稿引用不阻止删除（它不授予任何读取权，且它启用时会因清单校验失败而被拦下）。
- GET/POST /api/capabilities/*、/api/mcp-servers*：能力启停、CLI 通道覆盖与探测、MCP 服务器登记与删除。

服务只监听 loopback；目前假设可信本地操作者，不是带账户和角色的多用户部署。加上认证授权层之前，不要公开这些接口。

## 手动重启

先刷新 Maven 项目。Spring Boot 4 需要 Flyway Starter 和 PostgreSQL Flyway 模块，而不只是 flyway-core，参见[官方初始化说明](https://docs.spring.io/spring-boot/how-to/data-initialization.html)。

当前手工建立的 eap schema 没有 Flyway 历史。首次接管启动时，在 IDE 运行配置增加环境变量：

    EAP_ADOPT_EXISTING_SCHEMA=true

启动策略先检查预期旧表、字段和 embedding 可空状态，再登记基线并执行其后的迁移（当前至 V9）。不会 clean、repair、删除旧表数据或改写旧校验和。未显式允许接管时，已有表但缺少历史的库会停止启动并返回说明。

若结构检查不通过，先核对数据库，不要强行接管或 repair。首次迁移成功后移除该环境变量。空库按普通 V1–V9 迁移启动，不需要接管变量。

## 验证范围

后端单元测试覆盖图排序、断开与循环、必需隐私规则、未知能力、SQL 关联 AST、脱敏、无授权不读取知识、具体索引推断、必需节点阻塞、进程超时和并发限量输出，以及能力种类与可用性完整性、能力声明的事实与实际发布一致、规则包能力声明缺失/不完整/引用了不产出事实的能力、专家流程缺少规则包所需能力节点、跨能力规则仅在产出方执行时才命中（否则列为未判定）、MCP 工具的专家级授权与作用域解析、以及 MCP 会话不跨专家或跨执行复用的隔离规则。能力管理另有一组用例：停用被在用专家阻止并报出专家名、草稿引用不阻止停用、停用后清单校验与运行期解析都拒绝（且提示是「已停用」而非「未实现」）、每种能力都声明了管理入口、空但可管理的种类仍然可见而 HTTP 不可见、CLI 覆盖来源与探测行为、非法二进制取值被拒绝、MCP 服务器 id/工具/传输校验、登记默认停用且不信任、删除被在用授权阻止、以及已登记工具会出现在目录中。

前端回归测试覆盖图校验、错误反馈、规则库（能力声明与事实来源）以及专家、知识库、数据库资料页面初始化。常用命令：

    cd backend
    mvn -pl eap-runtime -am test
    cd ../frontend
    vp build
    vp test run
    vp lint apps/web/src packages/ui/src

DatabaseSchemaProbeTest 默认跳过，显式设置 EAP_CHECK_SCHEMA=true 才使用只读连接检查旧库。它不启动后端、不运行迁移。新授权与执行接口的端到端验收须在用户手动重启后完成。
