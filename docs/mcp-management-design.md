# MCP 管理与使用：参照 MCP Router 的对照方案

> 目标：在**不改变**「MCP 工具永不全局启用、会话按 `(执行, 专家, 服务器)` 隔离」这两条平台硬约束的前提下，
> 参照 MCP Router 的管理方式，改进 MCP 服务器的**管理**与专家对 MCP 工具的**使用**。
>
> 输出按「对照与结论 / 改造方案 / 实施步骤」三段组织。

---

## 一、参照对象：MCP Router 的管理方式抽象为五条机制

"MCP Router" 是一个被多支实现共用的名字（桌面版管理器 `mcp-router/mcp-router`、Go 网关、
Docker 本地网关、Python FastMCP 聚合器）。它们的界面不同，但**管理语义**可以归纳为同一组机制，
本文按这五条机制对齐，而不是照抄某个产品的页面：

| 编号 | 机制 | 具体做法 |
|---|---|---|
| **M1** | 集中式服务器注册表 + 连接状态 | 一张仪表盘列出全部服务器：传输方式（stdio 侧车 / HTTP+SSE）、启用开关、实时状态（connected / error / disabled） |
| **M2** | 工具发现 + 逐工具开关 + 命名空间 | 连上后跑 `tools/list` 自动发现工具，前缀成 `{server}__{tool}` 避免重名，然后**逐个工具**开关 |
| **M3** | 分组与作用域 | 服务器归入 Project；Workspace 像浏览器 profile，让客户端只看到当前上下文需要的那一组 |
| **M4** | 调用日志与统计 | 每次工具调用记录状态（success / denied / error）、目标服务器、耗时、调用方身份 |
| **M5** | 凭据外置 + 细粒度权限矩阵 | 下发 scoped key，按「服务器 × 工具」配置权限；凭据留在本地，不写进地址 |

## 二、对照与结论

### 2.1 结论总表

| 机制 | EAP 现状 | 结论 | 理由 |
|---|---|---|---|
| **M1** 注册表 + 连接状态 | 已有注册表（登记 / 修改 / 启用 / 信任 / 删除）；**没有连接状态**。`probe` 只回答"启动命令找不找得到"，结果是一次性提示，不落状态 | **改造后采纳** | 状态必须落到服务器上，让能力目录也能读；但措辞只能是「目标可达 / 目标不可达 / 未探测」，**绝不能显示"已连接"**——平台没有 MCP 客户端，那会是谎言 |
| **M2** 工具发现 + 逐工具开关 | 命名空间 `mcp.<server>.<tool>` 与 `{server}__{tool}` 是同一主意，已有；但**工具是一串逗号分隔的字符串，工具没有自己的状态** | **拆两步：清单化（本次落地）+ 放行开关（暂不画）** | 「放行这个工具 / 不放行」以"知道服务器发布了什么"为前提。平台跑不了 `tools/list`，就没有"服务器发布了但我没放行"这个信息源；画出来即是一个没有依据的开关 |
| **M3** 分组与作用域 | 授权是「专家 × 能力」的扁平表（`expert_mcp_grant`） | **分两层：按服务器分组呈现（本次落地）；工具组/授权包这一层不引入** | 分组呈现零成本且立刻可用；而"授权包"要等出现 3 个以上专家共享同一组工具才值得，否则是为假想问题加一层 |
| **M4** 调用日志 | 无 | **采纳，但落点不同**：进**任务/执行详情**，不进操作历史 | 操作历史的用途是回答"我做过什么、为什么这次结果变了"（见 [running-context.md](running-context.md)）。工具调用是执行内部事件，一次执行能打出几十条，混进来会让它读不出结论 |
| **M5** 凭据外置 + 权限矩阵 | 已有且更严：地址里出现凭据在登记时**当场拒绝**（`SensitiveData.containsSecret`），凭据一律环境变量注入；边界由 `expert_mcp_grant` 承担 | **已有等价物，不改；但这个词要换** | 单人本地场景里没有"给不同的人分权"这回事，"权限矩阵"是借来的服务端语汇。`expert_mcp_grant` 的真实含义是**第三方专家包的能力边界**——专家是配置而非代码，它拿什么必须显式写下。另记一条本地特有待办：凭据不下发，但**导出/分享配置时要能自动剔除**，这是本地场景唯一的凭据泄露路径 |
| （MCP Router 的）全局启用 | 启用即对下游客户端生效 | **明确不采纳** | EAP 的会话隔离正是为了防止这一点：一个 MCP 会话绑定会话标识、游标与协商结果，两个专家共用会互相污染（且是静默漏读，不报错） |
| （网关的）负载均衡 / 熔断 / 故障转移 | 无 | **不采纳** | 网关语义会向确定性流水线引入不确定性。若将来确需，也只能是"本次执行内熔断"，而非跨执行的故障转移 |
| （桌面版的）一键接入令牌 | MCPR_TOKEN + CLI | **不适用** | 消费方是平台内的专家执行，不是外部 AI 客户端 |

### 2.2 两个必须点破的坑

**坑一：逐工具放行开关现在画不出来。**
MCP Router 的逐工具开关建立在「已发现的工具全集」之上——先有 `tools/list` 的返回，才有"这一条要不要放行"。
EAP 现在没有 MCP 客户端，工具清单是操作者手填的声明。**"手填了又不放行"等价于"没填"**，
把这个动作做成开关只是多一个没有信息源的控件。
正确做法是：先把工具从"字符串"提升为"对象"（后端已预留形状），等协议发现可用后再加放行位。

**坑二：分组不能变成共享。**
MCP Router 的 Project 是"把一组服务器共享给客户端"，这恰恰是 EAP 用 `(执行, 专家, 服务器)` 三元组
隔离所禁止的。本次只采纳**呈现层**分组：授权界面按服务器归类，减少阅读与勾选成本；
**每个专家执行时仍然各自持有自己的会话**，分组不产生任何共享语义。

## 三、改造方案

### 3.1 数据形状

| 位置 | 现在 | 改成 | 说明 |
|---|---|---|---|
| `McpServerService` 存工具 | `[{"name":"search"}]` | 形状不变 | 后端注释已写明：与 `tools/list` 返回的对象同形，**将来可用真实握手填充而不需要迁移**——这是采纳 M2 的现成接缝 |
| 原型 `MCP_SERVERS[].tools` | `string[]` | `[{name, source, verified}]` | `source`：`declared`（操作者声明）/ `discovered`（协议发现，将来）；`verified`：是否经协议握手确认，现在恒为 `false` |
| 原型 `MCP_SERVERS[].probeState` | 无（探测结果是一次性提示） | `unknown` / `reachable` / `missing` | 由 `POST /api/mcp-servers/{id}/probe` 写入。**只描述传输目标，不描述协议连接** |

能力标识仍是 `mcp.<server>.<tool>`，且**只从工具清单中推导**：清单里没有的工具，目录里就不存在。

### 3.2 管理侧页面结构（能力目录 · MCP 工具）

1. **登记表单** — 工具输入保留"追加"语义，下方实时呈现**工具清单**：逐条显示工具名、来源、验证状态、移除动作。
   输入与清单是同一份状态，改任何一处另一处立即同步。
2. **已登记服务器** — 工具从一行文本改为**工具清单**，并新增**目标状态**标记（未探测 / 目标可达 / 目标不可达），
   旁边固定一句说明：目标可达 ≠ 已建立协议连接。
3. **发布的能力卡片** — 从工具清单推导，标注「由服务器 X 发布 · 操作者声明 · 未经协议验证」。

### 3.3 使用侧页面结构（专家工作室 · 清单）

- MCP 工具授权改为**按服务器分组**，每组抬头写明该服务器的状态：已启用/未启用 · 已信任/未信任 · 目标状态。
- 授权仍逐工具写入专家清单 `mcpTools`；分组只改变呈现与勾选成本。
- 没有「已启用且已信任」的服务器时，如实说明原因，不虚构工具、不退化为"全部允许"。

### 3.4 状态管理调整

| 项 | 调整 | 原因 |
|---|---|---|
| 工具是对象，不是串 | `tools` 从 `string[]` 改为对象数组，能力目录从清单推导 | 串承载不了"来源"与"验证状态"，也无法为将来的 `tools/list` 留位置 |
| 探测结果落到服务器 | `probeState` 写入服务器对象，不再是一次性提示 | 一次性提示会被重绘冲掉，能力目录读不到 |
| 表单与清单同一份状态 | 追加输入与逐条移除都写同一数组 | 两处各自为政必然出现"输入框里有、清单里没有" |
| **不新增**授权包/工具组状态 | — | 触发条件未满足，先不引入 |
| **不新增**调用记录状态 | 落在任务/执行详情 | 审计日志只记人的动作 |

## 四、实施步骤

### 阶段 1 · 原型（本次已完成）

- 范围：`docs/prototype/console.html` 的 MCP 工具子页 + 专家工作室的 MCP 授权块
- 内容：工具清单化、目标状态落服务器、按服务器分组授权、工具来源与验证状态如实标注
- 验收：行为级断言（登记 → 清单 → 能力目录 → 专家授权 四处同步；移除工具 → 能力随之消失；
  探测 → 目标状态出现在服务器行上；不含"已连接"字样）

### 阶段 2 · 后端（形状对齐，无迁移）

- 模块：`McpServerService` / `McpServerRegistry` / `CapabilityManagementController`
- 内容：`probe` 结果可被 `list()` 带回（目前只有一次性响应）；工具对象预留 `source` / `verified` 字段
- 风险：低——`tools` 已是对象数组，加字段不触发迁移
- 验收：`mvn -pl eap-runtime -am test`（含 `McpSessionIsolationTest`）

### 阶段 3 · 前端 Vue

- 模块：`frontend/apps/web/src/CapabilityManager.vue`、`ExpertManager.vue`、`api.ts`
- 内容：与原型同形的工具清单编辑器、目标状态、按服务器分组授权
- 验收：`vp test run`

### 阶段 4 · 有 MCP 客户端之后（本方案明确推迟，不提前画）

- 逐工具**放行**开关（依赖 `tools/list` 发现）
- 调用记录（依赖真实调用，落任务/执行详情）
- 工具组/授权包（依赖出现多个专家共享同一组工具）
