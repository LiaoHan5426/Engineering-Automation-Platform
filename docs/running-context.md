# 运行环境定位：个人本地单机

> 本文是**约束性**文档，不是背景介绍。任何设计、文档与原型改动都不得与它冲突；
> 发现冲突时改设计，不改这里。

## 一句话定位

**这是一个装在个人机器上、由一个人操作、只在本机运行的工程分析控制台。它不对外提供服务，
没有第二个用户，也不需要为"被部署到服务器上"做任何准备。**

这不是"现阶段先这样，以后可能上云"——恰恰相反：**上云是要被明确否决的方向**，因为整个平台的
价值主张（确定性优先、脱敏、专家授权、进程执行）都建立在"操作者拥有这台机器和被分析的代码"
这个前提上。

## 为什么这条定位容易被丢掉

它容易被丢掉，是因为我们在写文档时会不自觉借用服务端产品的语汇——那些词读起来很专业，但它们
各自带着一套隐含前提，一旦写进文档，前提就被一起引进来了：

| 借来的词 | 它悄悄带进来的前提 | 在本项目中是否成立 |
|---|---|---|
| 审计 / audit | 多个责任主体、需要追责与不可抵赖 | **不成立**——只有一个操作者 |
| 认证身份 / authenticated identity | 有账户体系，需要区分调用者 | **不成立**——本地可信操作者 |
| 权限矩阵 | 给不同的人分配不同的权 | **不成立**，但见下文：边界仍然要划 |
| 部署 / deployment | 有一台要发布上去的服务器 | **不成立**——安装到本机 |
| 并发限量 / 配额 | 多用户争抢资源 | **不成立**（限量的真实理由另有其事：防失控输出） |
| 对外接口加固 | 接口会暴露到不可信网络 | **不成立**——只监听 loopback |

## 定位决定什么：三张清单

### A. 该删掉的（按服务端假设长出来的东西）

- 用户、账户、角色、租户、会话归属到"人"的所有概念
- 鉴权中间件、登录态、对外服务加固、"加认证前不要公开接口"这类提示
- 多实例、水平扩展、容器编排、健康检查给编排系统用
- 云端凭据分发（下发 scoped key 那套）
- "Web 部署"作为一个**远程**投放目标

### B. 该保留、但理由必须重写的

这些机制现在是对的，但文档给出的理由是按多用户场景写的，理由错了迟早会有人按错误理由去改它。

| 机制 | 错误理由（不要再用） | 正确理由 |
|---|---|---|
| MCP 服务器 enable / trust 双开关 + 工具白名单 | 防止其他用户越权调用 | **你装进来的第三方 MCP 服务器默认不可信**；信任是你对"这个外部进程"的判断，不是系统对你身份的判断 |
| 专家必须声明 `mcpTools` 才可用 | 权限矩阵 | **第三方专家包的权限边界**：专家是配置，不是代码，它拿什么能力必须显式写下并被人看见 |
| MCP 会话按 `(执行, 专家, 服务器)` 隔离 | "审计无法区分发起人" | **状态与游标污染**：一个会话带着协商结果和半消费游标，串了会静默漏读。这条理由单人下依然成立，而且更硬 |
| 知识访问 deny-by-default + 逐条引用 | 合规 | **模型与专家都不能自证**，引用是让人能核；本机也要能核 |
| 脱敏（连接串、输出截断） | 防止泄露给其他租户 | **防止泄露进模型请求和导出产物**——泄露路径是出站，不是横向 |
| 主进程校验每个 IPC 入参 | 防被攻陷的渲染页 | 渲染的内容里有**别人的仓库、模型输出、MCP 返回**，它们是不受信任的数据，即使页面本身是你自己的 |
| 操作记录只记动作、不记重绘 | 审计合规 | 见下节：这份记录要能回答"我做过什么" |

### C. 该加强的（本地场景反而更需要的）

- **可回溯与可撤销**：责任主体唯一，"撤销"在多人场景危险，在单人场景是可以给的权利。
- **第三方隔离**：这是本地场景的主要风险面，比服务端场景更值得投入。
- **本机凭据存放**：keychain / 环境变量，不需要服务端分发，但**导出与分享配置时要能自动剔除**——
  本地场景的真实风险是"我把专家包发给同事，凭据跟着走了"。

## 威胁模型：主体换了

```
服务端场景（不是我们）：          个人本地场景（我们）：
  风险来自 别的人                   风险来自 我引入的东西
  ├─ 外部用户登录                   ├─ 第三方专家包（配置即代码）
  ├─ 越权访问他人数据               ├─ 第三方 MCP 服务器（外部进程）
  └─ 事后追责                       ├─ 模型输出（不可信观察）
      → 鉴权 / 审计 / 租户隔离      ├─ 被分析仓库里的内容（不受信任数据）
                                    └─ 出站：模型请求、导出、分享
                                        → 能力边界 / 第三方隔离 / 脱敏 / 可回溯
```

结论不是"安全可以放松"，而是**重心转移**：横向的、针对人的防护删掉；面向引入物与出站的防护
加强。任何以"反正只有我一个人用"为由放松 B/C 两类的改动都应被拒绝。

## 语汇约束

**不再使用"审计"这个词。** 用**操作历史 / 活动记录**。

理由不是字面洁癖：audit 在合规语境里绑定了"多主体 + 追责 + 不可抵赖"，用它会让人按那套前提去
设计（于是开始纠结"要不要防篡改"、"要不要签名"——单人场景下这些全是空转）。而"操作历史"直接
指向它真实的用途：

> 回答"我做过什么、为什么这次结果和上次不一样"，并支撑撤销。

由此产生一条比现在更强的要求：**操作历史应当能记下"改之前是什么"**。多人审计日志不敢这么做
（记录里存旧值有隐私与膨胀成本），单人本地没有这些顾虑，而缺了旧值就无法回答"为什么变了"。

既有的不变量（切页签不写记录）继续成立——它的理由是"记录要能被人读懂并据此复盘"，不是合规。

**不再使用"部署"指发布到远程。** 两种投放目标都运行在本机：

| 目标 | 实际形态 |
|---|---|
| 浏览器 | 本机浏览器访问 `127.0.0.1` 上的后端 |
| 桌面端 | Electron 打包外壳，后端作为本地 sidecar |

二者的差异只有"外壳能提供哪些 OS 服务"，没有一个是"远程"。

## 不做的事（因此不做）

- 不为"将来可能上云"预留抽象层。需要时重写比背着一个用错的模型便宜。
- 不引入任何用户表、租户字段、鉴权中间件，哪怕"只是留个字段以后方便"。
- 不为多人协作设计实时同步、冲突合并、锁。本机单人，文件的最后写入者就是唯一写入者。
