# 知识库、本地规则与模型调用的边界

状态：2026-11-08代码核对与用户问题说明；演进建议不是已实施的新执行框架。

## 当前实现事实

知识库不是模型专用附件。KnowledgeManagementService将脱敏文本存入本地PostgreSQL，按最多1500字符分块（不重叠）；保存内容SHA256，embedding_model为not-embedded，没有embedding调用或向量检索。KnowledgeRepository采用PostgreSQL全文检索与ILIKE关键词打分，中文用二元片段；查询最多500字符/24词，返回1～20条，每条摘录最多1200字符。知识库管理页搜索可直接返回片段、来源和分数，不调用模型。

knowledge.search是既有Capability。专家执行仅查询已授权的知识库，最多5条，并发布knowledge.granted、knowledge.matches及来源证据。固定DAG在enhanceWithModel=false时可直接完成本地解析、规则判定和知识检索。Chat的ExpertKnowledgeContextService先校验专家revision/启用/实时grant，在短事务中本地检索，再把有界引用送给后续Chat模型；预览接口本身不调用模型。SQL自主Agent由模型选择是否调用knowledge.search；检索仍本地执行，但工具选择和结论生成使用模型。

因此要区分：本地数据位置、本地计算、不使用生成模型、是否向外部模型传出摘录。这四项不是同一件事。选择外部模型Chat/Agent时，授权命中的摘录可能成为模型上下文；检索本地并不意味着整个流程离线。

## 三条路径

| 目标 | 路径 | 当前边界 |
|---|---|---|
| 查资料、查案例、定位来源 | 文本→本地分块/搜索→带来源片段 | 已有，无需模型；不是自由自然语言答案 |
| 按确定规则检查或执行固定步骤 | 结构化输入→RulePack/固定工作流→Capability→结果验证 | 已有这些机制；普通知识文档不会自动变成可执行规则或授权 |
| 理解模糊目标、综合多个材料、提出新方案 | 本地检索→模型分析/选工具→受控执行/独立验证 | Chat/SQL Agent已有有限切片；模型结果仍未验证 |

例：说明文档写“NOT IN遇到NULL有风险”，可本地搜到原文。要自动发现SQL中的问题，必须有AST事实提取和RulePack条件；本轮复杂SQL检查补齐该事实与规则后，不调用模型也能给出条件化提醒。文档写“遇到错误先清空目录”不会让平台自动删除文件；操作必须对应已注册能力、参数约束、授权及必要审批。

## 与常见RAG/工具调用的关系

RAG通常先检索相关片段，再将问题与片段交给生成模型。它让模型回答有依据，不等于取消模型；查询改写/重排也可能使用模型。检索本身可以是全文、关键词、向量或组合，不必先部署向量库。向量方案需要embedding模型，可本地或远端执行，通常不必用大型生成模型进行每次检索。是否更好应由真实查询/预期证据的命中率、排序、拒答和延迟评测决定。

Spring AI的RAG文档明确将检索结果放入模型上下文；工具调用文档明确应用执行工具，模型只请求调用。依据：[Spring AI RAG](https://docs.spring.io/spring-ai/reference/api/retrieval-augmented-generation.html)、[Spring AI Tool Calling](https://docs.spring.io/spring-ai/reference/api/tools.html)、[PostgreSQL全文检索](https://www.postgresql.org/docs/current/textsearch-controls.html)。这支持本项目“检索/规则可本地，模型只承担需要理解和规划的部分”的分层；不能从官方支持RAG推断当前EAP已有完整语义搜索或知识自动执行。

## 现有不足与建议顺序

1. 文本已有新增/列出/删除，2026-11-12补齐原位正文更新：`PUT /knowledge/{base}/documents/{document}` 携带原正文SHA-256，服务端锁定同知识库文档、核对旧哈希，并在同一事务更新标题/哈希、删除旧分段、插入完整新分段。新增与更新复用同一分段函数，文档ID及知识库关系不变，不用删旧再新增模拟更新。旧正文哈希返回409 `KNOWLEDGE_DOCUMENT_CHANGED`，中英文资源同步；只承诺正文内容的乐观校验，尚无不可变文档版本历史/发布回滚合同。分块没有段落/重叠语义。摘录已改为围绕首个可定位的匹配词保留前文，最多1200字符且不拆开代理对；完整分段先脱敏再截取，避免截断凭据语法后无法脱敏。没有可定位词时仍取开头，不宣称支持任意词形定位或语义摘要；排序、授权SQL与返回命中身份不变。

前端正文详情提供独立编辑Dialog，关闭未保存编辑确认，保存后按同文档ID读回标题/正文再刷新列表；原编辑内容在失败时保留。独立Mock同步哈希合同和检索当前正文，不侵入正式源码。已发送到模型的历史引用不重写；下一轮授权检索读取新分段，知识派生记忆的清理机制沿用原路径。本轮没有扩大专家授权，也没有模型调用。验证及剩余边界见[当前台账](../planning-status.md#knowledge-document-update-validation)。
2. 词法相似不是问题等价；同义词、语境、否定、冲突和过期文档尚无完整治理。不要仅凭检索分数自动执行。
3. 已验证经验若要转为本地操作，先人工整理为有适用条件/前置检查/输入输出/风险级别/失败策略的规则或固定工作流，关联原文和版本，复用现有注册与审批机制；不另造“知识执行器”。
4. 下一最小切片可提供明确的“仅本地检索/确定性分析”入口与模型调用原因展示，建立真实问题/预期证据基线，再补正文版本管理。只有词法检索质量不足时再评估同义词、混合检索或本地embedding。
5. “严格不调用模型”模式应明确拒绝模型回退；“优先本地”模式遇证据不足只解释缺口并按用户许可升级。自然语言意图到任意工具的通用编排不是目前确定性能力。

## 本轮验收口径

复杂SQL将有效语法和完整结构覆盖分开；CTE/子查询/聚合/窗口未完整遍历时标记部分证据，不把外层表/连接数量当全查询事实。NOT IN规则明确NULL/反连接语义，不承诺NOT EXISTS等价或性能提升。真实模型与独立合成数据样例验证、知识库本地读写/授权、系统缩放、用户体验接受分别记录在模块组合接续；不以模型答案正确率或样例通过声称任意SQL可靠。
