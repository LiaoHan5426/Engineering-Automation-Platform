## 1. 现状：两套结构不能直接互相覆盖

| | 本机历史（现状权威） | 后端消息图（V2，新底座） |
|---|---|---|
| 存储 | `localStorage['eap.chat.history.v1']` | `eap.chat_conversation` / `eap.chat_message` |
| 结构 | 线性 `transcripts: Record<convId, ChatTurn[]>` | 不可变树：`parent_id` + 同级 `version` |
| 分支 | 无（切换兄弟版本靠覆盖式草稿，图里没有父子关系） | 一等公民：编辑/重生成产生新节点，旧节点保留 |
| 执行身份 | `ChatTurn.executionId` 可能为空，也可能指向真实执行 | `chat_message.execution_id` 仅挂在 ASSISTANT 节点，受约束校验 |
| 内容分层 | `text` / `reasoning` / `proposal` / 各类 context 混在一个 turn | `snapshot` 只存 `id/role/text` + 可选 `thinking/citations`，bounded |

关键事实：本机线性序列没有父节点信息，无法无损还原成"哪条回复是哪条提问的兄弟版本"；
其 `executionId` 也只是本机声称，未经服务端核对（`local-claim`）。
把线性数组直接灌成消息图会凭空捏造分支拓扑与执行证据，属于伪造——这正是"不迁移、不导入"的技术依据，
也是"不保留"不会造成信息损失的场景：旧记录本就不能作为服务端事实。

2. **用户明确选择"现在清除"**（2026-11-21，经确认追问就"认可策略"与"立即清除"二选一后确定）。

### 2.1 已落地：一次性启动清理

- 位置：`frontend/apps/web/src/main.ts`，在挂载 App 之前调用 `clearLegacyChatHistory(chatStorage(localStorage))`；
  放在应用入口而非聊天视图，确保无论首个打开的是哪个页面都会清理，且不干扰组件级会话恢复测试。
- 逻辑（`chatHistory.ts`）：以哨兵键 `eap.chat.history.cleared.v1`（同 API scope 前缀）保证**只清一次**——
  首次启动删除旧历史键并写哨兵；此后每次启动只检查哨兵，因此清理后新建的会话、后续刷新都不再被删。
  先写哨兵再删历史：中途失败则下次重试，不会"丢了历史却没留标记"。
- 清理范围**仅** `localStorage['<apiScope>.eap.chat.history.v1']` 一个键，内含会话列表 / 消息 / 草稿 / scratch；
  不触碰后端消息图、附件原件、`eap.chat.prototype`（sessionStorage 原型临时态）、工作区偏好等其他本机键；
  不 clean / repair / baseline 数据库。
- 不可逆提醒已向用户明示：当前所有未迁移的本机会话将永久丢失，且无法从后端图恢复（V2 此刻为空、从未写入本机 turns）。
- 验证：一次性清理单测 5 项 + "清理后空会话启动"集成测 1 项通过；chat 定向回归 42 文件 263 项通过；类型检查、生产构建通过。

3. 新图只承接**切换后新产生的消息**；切换开关由切片 C 的前端投影改造引入，且必须先通过切片 A 的交互接受，本方案不启用它。
4. 本机旧记录现已清除，不再有"本机（旧）/服务端（新）"的长期分区需求；切片 C 上线后列表只呈现服务端会话。

## 3. 不做人工整包导出、不做反向导入

- 取消原方案 §3 的"本机历史整包导出（`local-claim`）"：既然旧记录不保留，无须为其生成留档文件。
- **区分既有功能**：`features/chat/chatExport.ts` 的"当前展示会话 Markdown 导出"是既有用户功能，继续保留；
  它不是本方案要删除的"本机历史整包导出"，不得据此一并移除。
- 不提供任何把本机历史反向导入为服务端消息图的入口；旧记录的 `executionId` 一律不提升为 `chat_message.execution_id`。

## 4. 受控导入：不适用

原方案 §4 的 6 项前置条件随"不保留 / 不导入"决策一并作废。若将来另行提出导入需求，须重新立项并重新审阅，
不得引用本方案作为授权。

## 5. 清理的边界约束（已按 §2.1 落实）

一次性启动清理遵循以下约束：

1. **只清本机历史一个键**：`localStorage['<apiScope>.eap.chat.history.v1']`；
   不触碰后端消息图、不触碰附件原件、`eap.chat.prototype` 及其他 localStorage 键；
2. **幂等**：哨兵保证只清一次，不误删清理后新建或后续刷新产生的会话；
3. **失败安全**：storage 缺失或抛异常时静默跳过、不阻塞启动；先写哨兵再删历史，中途失败下次重试；
4. **不可逆已告知**：丢失的会话不能从后端图恢复（V2 从未写入本机 turns）；
5. 全程不 clean / repair / baseline 数据库，沿用 [running-context.md](../running-context.md) 的约定。
