# CLI、MCP 与 Agent 工具接入：运行边界及收敛计划

状态：2026-10-24。共享工作区、单一 Git 入口和后移跨重启接管已落在当前工作区。日常服务授权根未改。不代表跨重启清理已经完成，也不授权调度、审批、MCP、Harness 或仓库写入。

## 1. 接入选择：先复用，再做薄适配

| 需求 | 推荐路径 | 不应附带建设 |
|---|---|---|
| 已有本地 Git、搜索等确定性能力 | 现有 Capability / Handler → CLI 或 Java 实现 | MCP 包装服务、第二条命令组装路径 |
| 自定义 CLI 操作 | 现有程序/操作登记、模板及 ProcessExecutor | 任意 Shell 接口、独立进程管理器 |
| 外部系统已经提供 MCP 工具，或有互操作需求 | 成熟 SDK / Spring AI MCP 集成 → 目标服务器 | 自研协议栈、复制服务器内部执行器 |
| 模型选择工具 | Spring AI 工具编排 → EAP 受控能力入口 | 第二套 Provider、工具循环和工具注册中心 |
| Codex、Hermes 等外部 Agent | 独立适配器 → 对方支持的 CLI/协议入口 | 把整个 Agent 伪装成 ChatModel，或复制其运行时 |

CLI 与 MCP 是接入方式，不是安全等级。MCP 可以复用外部工具，不自动提供文件系统沙箱、授权或进程恢复。不为形式统一将已有本地能力强制改成 MCP。

## 2. 接入与运行逻辑

```text
UI / Chat / Expert / Mission
  → EAP 应用入口：绑定上下文，检查能力与执行策略
  → 现有 Capability / Handler
      → 本地能力构造 argv → 共享 ProcessExecutor → 本地进程
      → MCP 薄适配 → SDK → 已授权的服务器/工具
  ← 结构化结果、错误及证据
  → 调用方展示、持久关联或投影
```

这是职责划分，不要求为每一层新建接口、类、表或注册中心。

- **共享运行时**提供工作区、授权根、本机操作者标签及显示标签。能力解析/启停、路径范围、参数模板及环境策略分别检查，不能互相代替。
- **Capability / 操作定义**拥有操作语义、参数 schema、命令模板和结果转换。Git 的命令数组只能由已有 Git 能力入口构造；调用方不得检查类型后自己重拼命令。
- **ProcessExecutor**拥有实际启动、执行号、超时、输出限额和退出观测；截断与脱敏复用通用处理，落库或外发前确认已处理。通用取消行为只承诺真实验证过的部分。
- **MCP 适配器**负责现有授权桥接、服务器/工具映射和结果转换，协议与传输交给 SDK。远端工具的进程由服务器管理，EAP 不接管远端 PID。
- **Mission**负责子执行记录、关联及最近状态投影，不负责组装 Git 命令或另一套进程管理。平台执行号应经能力入口传给共享执行器；只局部扩展现有上下文，不绕过能力实现。
- **Plugin / Skill**分别贡献界面与指令，安装、Manifest 申请、模拟审批都不产生实际授权。

Chat、Expert 与 Mission 复用同一操作语义和执行入口，允许不同场景有更严格策略。不得以新增入口绕过已有能力停用、目录或参数检查。保留各注册表原有职责，不创建包罗所有扩展的万能注册中心。

## 3. 工作区、配置与权限

**2026-10-27 再纠偏**（详见 [运行环境定位](../running-context.md)）：Java 默认是**用户机器上的本地服务**，不是模型厂商式远端多租户后端。本地服务数据目录中的模型连接与本机工作区绑定属于本机配置，合法。禁止的是把 EAP 做成公有云去代持**另一台机器**的路径/密钥，或把浏览器自报路径当成写权限。

产品默认 UI 与本地 Java **共置**；`ProcessExecutor` 在本机执行 git/rg/已登记 CLI。纯异机浏览器连远端 Java **非默认产品**。不做隔离云 VM。

工作区身份不从模拟仓库标签、sourceRef、模型文本或请求自报路径推导。`eap.runtime.authorized-root`（及旧键回退）描述**本 Java 进程**的进程绑定根；校验实路径、目录及该进程边界。cwd 检查不是操作系统沙箱，仍需核对工具实际访问的仓库/资源边界。

本机单用户无需为此新增远程认证系统。`local-operator` 是审计标签，不是认证；`resolveFor` 只证明能力可解析及相关启停/范围条件满足，不完成路径、参数和执行策略授权。

同机进程绑定配置成为该 JVM 的事实源，Chat 和 Mission 共同读取；Mission 不依赖 `com.lh.eap.ai` 的常量、显示算法或 AI 专属配置。迁移时明确新键和旧 `eap.ai.authorized-root` 的兼容期限：旧键只作显式回退，新旧冲突则拒绝相关操作并说明原因；可空。不能回退到任意 cwd、上级目录或全盘授权。文档更新不改变既有部署配置。

CLI 使用 argv，不拼 Shell；参数模板及环境按操作需要限制，不把某一 Windows 操作的变量清单推广为所有 CLI/MCP 的固定要求。二进制发现、配置覆盖、超时及输出上限复用现有渠道。

## 4. MCP 接入流程与责任

1. 登记受信服务器来源、传输、必要配置与允许工具；配置保存和目标探测不算连接成功。
2. 使用锁定版本的成熟 SDK 完成连接、初始化/协商、真实发现和 schema 校验；具体协议流程以该版本为准，不手写另一套协议。
3. 将当前调用上下文映射到现有服务器/工具授权，校验输入后调用。发现工具、只读标注及 Manifest 申请均不等于授权或隔离。
4. 转换结果、协议错误、超时与取消确认，保留服务器/工具身份。连接成功、调用成功和业务验证通过分别展示。
5. 按 SDK 与服务器语义管理连接/会话，避免跨操作者、专家或执行泄漏状态。重连、重试与重放须有幂等性和范围依据，不默认重放副作用操作，不自研连接管理框架。

本地 stdio 服务器仍是本机程序，其命令、参数、环境、文件系统权限和生命周期由实际启动方限制。远端 HTTP 使用服务器支持的认证方式；EAP 仍控制调用目标、工具范围及输出处理。本地命令沙箱不自动覆盖远端 MCP。MCP Roots 是上下文提示，不能当成强制访问控制。

先复用 `McpServerService`、现有授权和会话结构，再核查缺失协议适配。登记、人工工具清单、地址可达和 Fake Handler 都不能证明真实工具可用；发现与授权调用须有真实协议证据。审计中的“尚无客户端”等结论仅对应其检查基线，实施前重新核对。

## 5. 单步执行与恢复边界

创建 Handoff / Mission 不执行。进程成功只证明单次执行结果，不等于 Mission 完成；当前切片保持 `status=created`、`verification=not_requested`、`grant_state=none`。分析任务、对话内存和浏览器模拟状态不代替 Mission 的持久生命周期。

取消请求、内存取消标记和退出证据是不同事实。未记录 PID 不能证明未启动；父 PID 消失不能证明子进程都退出。证据不足不得写成已确认的 `CANCELLED` / `INTERRUPTED`，也不得据此销毁不明归属进程。

跨重启接管后移为独立能力，不是接通只读 Git 的前置条件。Mission 启动恢复现在只记录未知并保持在途，不再按进程号销毁，也不把缺进程号或父进程消失写成 `INTERRUPTED`。同一次进程内的取消仍要等真实退出。既有通用取消和真实进程回归保留。

证据不足时区分“执行状态”和“观测可信度”，记录结果未知及原因。字段/枚举由具体契约决定，不在这里新增表设计。未知执行会阻塞下一次启动，不自动转成功、失败或中断。人工解除机制尚未实现，不能把这条阻塞算成可恢复 Mission。

未来确需进程接管时，先评估已有监管或操作系统机制，单独证明启动/持久化窗口、身份、子进程归属和退出确认。PID、启动时间、用户及可执行文件匹配仍不能代替完整进程树证据。

## 6. Codex / Hermes 对照与适用边界

以下为 2026-10-24 查阅官方文档后的设计借鉴，不是对两者源码的完整审计，也不代表 EAP 已完成相同能力。

| 官方资料呈现的做法 | EAP 应借鉴 | 不直接搬入 |
|---|---|---|
| Codex 分别配置 MCP 连接/工具和执行安全策略 | 分离接入配置、调用范围与实际运行环境 | 为每个工具复制一套沙箱或审批系统 |
| Hermes 内置工具按 toolset 启停，MCP 接入外部服务器 | 本地工具复用现有能力目录，外部工具通过薄适配接入 | 替换 EAP 注册表或复制完整 Agent Runtime |
| Hermes MCP 支持服务器配置、发现、工具过滤及连接状态 | 区分已配置、已连接、已发现、可调用和调用结果 | 把保存配置当成功，或先建市场再打通一个工具 |

由此建议的接入顺序是：选择已有能力或目标服务器 → 配置并限定范围 → 检查依赖/连接 → 发现或解析 → 执行策略检查 → 单次调用及证据 → 必要时再扩展生命周期。不得反过来为一项只读调用先造完整任务调度器。

官方依据：[Codex MCP](https://learn.chatgpt.com/docs/extend/mcp?surface=cli)、[Codex 安全与审批](https://learn.chatgpt.com/docs/agent-approvals-security)、[Hermes 工具与 Toolsets](https://hermes-agent.nousresearch.com/docs/user-guide/features/tools)、[Hermes MCP](https://hermes-agent.nousresearch.com/docs/user-guide/features/mcp)、[MCP Tools](https://modelcontextprotocol.io/specification/latest/server/tools)、[MCP Roots](https://modelcontextprotocol.io/specification/latest/client/roots)。链接跟随官方版本，实际集成须锁定 SDK/协议版本。

## 6A. Harness 复用优先：满足需求即可，不复制底座

Harness 指围绕模型提供工具调用、上下文/会话、事件、审批和运行环境等能力的执行宿主；各产品实际支持范围不同。它不是 MCP 的同义词，也不要求 EAP 自行实现一个新的 Harness。

接入决策顺序：已有确定性能力能完成就直接使用；需要模型推理时复用现有 Spring AI；需要完整编码 Agent 行为时，先评估已有 Harness 的受支持入口。优先配置和组合成熟实现，只有明确的业务缺口才局部扩展 EAP。不能为了复用 Harness 而把简单 Git 查询升级成模型调用或额外付费任务。

EAP 主要保留产品入口、可信仓库绑定、任务/交接关联、调用边界及独立验证；所选 Harness 已可靠提供的工具循环、上下文管理、会话事件和执行环境直接复用。EAP 记录外部会话/运行号和必要证据，不镜像整套内部状态机；对方的任务完成事件也不能直接等同 EAP 验证通过。

接入前以需求清单核对官方接口、版本、许可、平台支持、凭据、成本、工具限制、审批交互、取消及恢复的实际语义。任务自动化可评估 Codex SDK，深度客户端集成可评估 app-server；这是候选方案，不是安装或替换现有适配器的授权。App-server 的接口和传输成熟度须按锁定版本逐项核验，不因官方示例存在就认定生产可用。Hermes 同样先核对其受支持接口，不假设与 Codex 协议兼容。

边界只保留必要的两层：EAP 决定是否委派以及允许的仓库/操作范围；Harness 在其能力范围内执行并报告。优先把限制传入对方受支持的配置，而非复制一套进程监管；限制无法表达或无法验证时，缩小范围、使用已支持的隔离环境或暂不开放该操作，不能静默放宽。真实变更仍由 EAP 独立检查 diff、重建和测试。

新增底座必须回答：“现有 CLI、SDK、MCP Server 或 Harness 为什么不能满足这项已授权需求？”只有具体缺口和替代方案比较成立，才设计最小补充；不以远期扩展性为理由先建调度器、通用沙箱、会话引擎或第二套审批系统。

参考：[Codex SDK](https://learn.chatgpt.com/docs/codex-sdk)、[Codex App Server](https://learn.chatgpt.com/docs/app-server)。本节为复用原则，不宣称已安装、验证或选定某个 Harness。

## 7. Cursor 下一轮调整清单

本节清单中的共享运行时、单一 Git 入口和后移接管已在当前工作区实现。日常授权根未改。下面保留为对照，不代表还要再做一轮进程接管：

1. 在实际含未提交 Mission 执行代码的检出运行 `git status`，记录 HEAD、diff 和既有 `expert-sdk` 改动；不要从旧 worktree 覆盖新文件。核查下列类及测试后列出准确修改清单。附一份简短的复用判断：本轮只读 Git 继续用本地能力；未来 Agent 需求先比对已有适配器和 Harness 的能力缺口，不在本轮安装或搭建新 Harness。
2. 抽离最少的共享工作区/根/本机标签配置，替换 Mission 对 AI 包的引用；Chat 共用它。测试旧键兼容、冲突拒绝、空根拒绝与配置不扩权。不更改日常服务根。
3. 局部扩展 `GitCapability` / 现有上下文以传递平台执行号，复用既有 ProcessExecutor。删除 `MissionGitExecutionService` 自行拼 `[binary, status]` 的路径和对 `DefaultProcessExecutor` 的身份采集耦合，保持既有 Handler 调用兼容。策略检查保留，但不再复制命令模板。
4. 后移自动重启销毁/接管。恢复只记录未知并阻塞重跑；不将未记录 PID 或父进程消失转换成已确认中断。不保留只给测试用的身份判断空壳。保留实际退出证据要求、记录及投影一致性；不改已应用迁移，需要变化时新增增量迁移。
5. 同步单步契约、roadmap 和实现说明，明确保留、替换、后置项及未知结果的处置边界。先不扩展调度、审批、自动续跑、通用进程监管或写仓库。
6. 验证相同 Git 操作只有一个命令构造入口、Mission 无 AI 包依赖、平台执行号贯通；覆盖禁用、越界、非法参数/环境、配置迁移、并发和未知结果不自动重跑。保留已有真实进程回归。在经批准的隔离仓库验证实际 Git；单元测试不代替运行证据。
7. 按变更运行开发指南中的后端回归及前端检查，分别报告实际数据库、真实进程、单测及未验证项。交付 diff、文件理由和可操作页面供验收；排除 `expert-sdk` 既有改动，不提交、不推送。

不要仅为本轮清理创建新的“统一执行框架”；新增底座前必须提供当前业务需求、已有入口缺口、局部扩展方案比较及最小验收证据。完整取消/恢复/重连等只在切片明确要求时实现；保留已有保护，但不把远期验收矩阵全部变成本轮开发前置条件。

## 8. Hermes 对照：防止诊断流程演变为底座（2026-10-24）

本次为代码与官方资料静态审查，不运行 Agent，不更改策略。当前 CodexAdapter 没有另建模型/工具循环，ProcessExecutor、超时、脱敏、JSONL 结果映射和独立 Git 证据属于合理薄适配。但模型缓存证据状态、userAuthorizedTrial/trialConsumed、系统临时目录和 .eap-codex-test 标记属于历史付费试验的限制，不应无条件升级为生产调用合同；未来移出时仍须保留明确任务授权、可信目录绑定和预算边界，不能直接删除后全开放。

Hermes 官方 Codex skill 的单次委派复用已有 terminal/process：选 workdir，执行 codex exec，观察结果并复核变更。它不是 MCP 接入，也不要求先实现自有 Harness。可选 codex app-server runtime 是另一条较深集成：复用 Codex 原生执行循环、工具和审批事件，不能据此要求 EAP 当前实现该整套桥接。两者都支持“宿主只做必要适配”的方向。

EAP 不应把版本、help、独立 features list、测试门控和多轮报告逐一串成所有调用的业务前置条件。版本/help 属于兼容诊断；features list 只证明配置解析。保留已有测试但不要求每轮重复执行，只有具体失败和改动才触发针对性检查。没有真实运行授权时如实暂停，不用继续开发诊断层来替代业务进展。

推荐最小生产目标仍为：显式授权的任务及可信工作目录 → 一次 Codex CLI 调用 → 有界输出/事件与退出结果 → EAP 独立 diff/文件/测试验证。模型选择和认证优先交给已配置的 CLI，不另建 EAP 模型可用性认证体系；若业务要求指定模型只传必要参数并处理真实错误。明确拒绝可提前阻断，但缓存没有模型不等于模型不可用。任务批准不等于沙箱放权，提示文本不等于安全边界。

当前用户仅要求收敛审查，生产接线和移出试验限制均需按后续具体授权实施。下一步不要因本节新增数据库、通用诊断服务、连接注册表或另一个 Harness。历史沙箱拒绝属于环境/配置诊断，不是“需要更多 EAP 底座”的证据。

参考：[Hermes Codex skill](https://raw.githubusercontent.com/NousResearch/hermes-agent/main/skills/autonomous-ai-agents/codex/SKILL.md)、[Hermes 可选 Codex runtime](https://hermes-agent.nousresearch.com/docs/user-guide/features/codex-app-server-runtime)。仅借鉴责任分工，不照搬其中 PTY 必选、旧参数或更宽权限建议；实际非交互传输、权限和版本以本机可验证合同为准。
## 9. 用户本地配置与切换：替代固定接入（2026-10-24）

用户明确要求本地可配置和切换。后端进程不应成为连接和 Agent 选择的唯一决策者；本地界面拥有新增、编辑、启停、默认选择与会话选择入口，保存后无需重启。后端作为本地运行服务承担配置持久化、凭据保护、参数验证及所选连接执行，不将密钥交回浏览器，不以部署环境变量代替产品设置。

当前 EngineeringAiConfiguration 在启动时从唯一模型构造 ChatClient，EngineeringChatService 长期持有 final client，Request 无连接选择；这是现有限制，不是目标架构。Spring AI 2.0.2 官方支持程序化及多个 ChatClient，动态选择不要求自研模型协议。移除供应商单例自动配置对选择权的控制；Starter 可移除或仅保留默认引导，复用已有 Spring AI 供应商实现、工具编排和观测配置。环境配置最多作为可见默认/兼容导入，不覆盖用户保存选择。

产品区分两类可配置目标：模型连接（供应商、端点、模型、凭据）与外部 Agent（Codex/Hermes 等本机入口和其配置）。二者不伪装成同一种底层协议，也不在本轮做成同一个设置平台。不要求所有 Agent 经 Spring AI。选择记录标识与必要配置修订，执行开始时捕获快照，不原地修改共享客户端影响在途请求。默认选择影响下一次发送，切换需明确后续消息会发往不同目标，禁止静默迁移或外发旧会话。外部 Agent 已配置的默认模型/认证由其自身处理，用户也可按其支持显式选择。

最小切片已落地“保存、选择、切换现有 OpenAI 兼容连接”，到此为止。保存写在本地 `.eap/model-connections.json`，密钥不回显。环境配置只在用户还没有保存连接时作为默认。对话绑定选定修订；在途请求持有当时的客户端，切换不改这个客户端，也不调用模型、不授予工具权限。目标变化需要确认，确认后清空该对话的模型记忆，不把旧会话发给新供应商。状态观察按该修订记录。真实付费模型未调用。

连接管理是工程工作台的辅助设置，不是产品主线，也不把默认入口改成通用聊天。任务、仓库、执行证据和交付仍是主线。本轮不扩展供应商目录、模型市场、自动路由、负载均衡、统一推理网关或自研认证体系。

模型连接与外部 Agent 保持两种入口。选择 Codex 或 Hermes 时复用该 Agent 自己的运行入口和已有配置，不要求先保存 Spring AI 模型连接，也不由 Spring AI 接管它的内部工具循环。没有配置模型时，本地确定性能力和手工 Builder 仍可使用。

旧 SQL 流程的压缩、缓存和失败回退只属于 SQL 兼容桥。缓存按该桥使用的连接修订分区，失败仍是 `AI_NOT_CONFIGURED`，确定性结果继续作主结果。这套规则不套用到普通对话记忆，也不套用到外部 Agent。

本节覆盖旧规划“Spring AI 环境属性是唯一连接事实源”和“不提供本地配置/切换”的长期约束；S1 的只读配置仍保留为历史切片事实。参考：[Spring AI 多模型及程序化 ChatClient](https://docs.spring.io/spring-ai/reference/api/chatclient.html)。
