# 知识库页面的信息架构评审

> 主题：以「知识库」菜单为例，论证单页堆叠造成的限制，评估二级页面 / 弹窗 / 抽屉三类改造方案，并给出推荐选择。
> 目标运行环境：Electron 桌面壳（选型已确认，理由见 [desktop-spec.md](desktop-spec.md)；
> 本文早期版本提到的「与既有决策冲突」已随该决定关闭）。
> 文中所有结论都附带实测数据与可复现步骤，验证方法见第 8 节。
>
> **落地状态（2026-10-10）**：第 8 节的 K1–K8 已全部落进 `docs/prototype/console.html`——
> 知识库三页签 + 抽屉 + 模态、规则库四页签、专家工作室四页签、数据库资料新增/编辑进抽屉且删除走模态。
> 行为级回归共 405 项断言（`verify-console.js`），含页签互斥、切页签不写操作历史、抽屉未保存拦截、
> 模态影响面与 409 阻断；真实 Chrome 逐状态截图核验通过。运行目标已同步为 Electron。
>
> **落地状态（2026-10-12，后续演进）**：这里的「页签」已进一步升级为**层级路由**——
> URL 成为唯一真源（`#<area>` 集合页、`#<area>/<itemId>/<face>` 条目页的某个面、`#<area>/<mode>` 集合级模式页），
> 不再是同级页签切换。知识库因此有了真正的集合页 / 条目页 / 跨库检索模式页，规则库与专家工作室同样，
> 详见 [navigation-structure-refactor.md](navigation-structure-refactor.md)。
> 同一轮还补齐了抽屉组件（未保存拦截）、模态的 409 阻断态、设计令牌层与焦点环。
> 行为级回归增长到 484 项断言，全绿。

## 1. 结论摘要

1. **知识库页面确实存在单页堆叠问题，但不是最严重的一页。** 它在单一滚动区内并列了 4 类互相独立的工作面（知识库管理 / 文档管理 / 跨库检索 / 文档预览），共 20 个控件、6 个标题层级、0 个二级页签。
2. **问题的性质不是"东西太多"，而是"层级被压平 + 作用域被混装"。** 一个只读的「检索」和一个破坏性的「删除知识库」处在同一视觉平面；检索的作用域是**全部已授权知识库**，却被画在**某一个知识库卡片内部**。
3. **平台自己已经给出了解法。** 能力目录与桌面外壳都用二级页签把 49 / 27 个控件切到每页最多 21 / 6 个，而知识库、规则库、专家工作室是该规则的三处例外。
4. **推荐：知识库改为二级页面（页签），与能力目录/桌面外壳统一**；页签 = `知识库` / `文档` / `检索`。一次性事务（新建、重命名、新增文档）用**抽屉**；破坏性确认（删除知识库/文档）用**模态**。**不推荐**用弹窗或抽屉承担主导航。
5. **横向评估结论：规则库比知识库更需要改造**（30 控件 / 11 标题 / 4 卡片 / 0 页签）；专家工作室次之；数据库资料中度；概览、任务、SQL 分析室不需要动。
6. 顺带发现两处**与本次改造无关、但应当一并修**的既有缺陷：全平台没有任何 URL 状态（无深链，也就没有"二级页面"的位置）；破坏性确认被渲染成页面内的消息行，位置与触发点分离。

## 3. 三类问题的具体表现

### 3.1 层级缺失

- **标题语义重叠**：页面 `h1` 是「知识库」，左卡 `h2` 也是「知识库」。前者是页面主题，后者是列表标题，同名但不同层，读者无法从标题判断自己在哪一层。
- **平级并列，主次不分**：`h2「知识库」`（管理）与 `h2「检索」`（查询）是同级标题，并列在同一个滚动流里。检索是只读的高频动作，管理是低频的写入动作，二者被赋予相同的视觉权重。
- **破坏性动作与常规动作同排**：[重命名][删除知识库] 与 [＋ 新建知识库] 采用同一按钮族，删除仅靠 `danger` 配色区分，且与「重命名」紧邻。
- **作用域与容器不匹配**：`#kbQuery` 画在左卡的「知识库」`h2` 之下，但 `runKnowledgeSearch()` 的作用域是 `EXPERTS.filter(e => e.enabled).flatMap(e => e.knowledge)`——**所有已启用专家被授权的知识库**，是跨库查询。容器暗示"搜这个库"，实现是"搜所有库"，只有一行 hint 文字在纠正。
- **平台自身的 IA 规则在此被打破**：`docs/frontend-prototype.md` 明确写着"a page's sub-pages are tabs inside it, not rail entries"，而知识库是这条规则的例外之一（另外两处是规则库、专家工作室）。
- **连"二级页面"的落脚点都不存在**：全平台检索 `location.hash` / `pushState` / `replaceState` 均无命中——没有路由。这意味着当前架构里"第二层"既没有视觉表达，也没有地址表达。

### 3.2 操作路径别扭（逐条可复现）

以下场景均在 jsdom 中实际驱动交互后记录，不是推测。

**场景 A｜只读检索静默改写浏览/编辑上下文**
1. 进入「知识库」（首屏不自动选中；点一台库才开始，这里点 `dba`）。
2. 在「检索」输入框输入 `索引`。
3. 点击最后一条命中（属于 `orders-runbook` 库）。
4. 观察：`selectedKbId` 由 `dba` 变为 `orders-runbook`，右栏标题从「文档 · dba」变为「文档 · orders-runbook」，左列表高亮整体迁移。

> 实测：`点击后 selectedKbId: dba -> orders-runbook` / `右列标题: 文档 · orders-runbook`。
> 问题：一个**只读查询**变成了**导航动作**。用户如果正在编辑 `dba` 的文档，一次检索就把上下文切走，且没有任何"你已离开 dba"的提示。

**场景 B｜悬空表单不随选择收起，输入残留**
1. 点击 [＋ 新建知识库]，在「知识库标识」里输入 `tmp-typed-value`，在「名称」里输入半截文字。
2. 直接点击左列表里的另一个知识库。
3. 观察：`#kbCreate` 的 `display` 仍为 `block`，两个输入框的值原样保留。

> 实测：`切换后 kbCreate.display = block；残留 id = tmp-typed-value；残留 name = 输入到一半的名称`。
> 问题：页面上同时存在两个"进行中的编辑"，而没有任何未保存状态提示。用户很容易带着未提交的创建意图去做别的事，之后忘记或误提交。

**场景 C｜破坏性确认条出现在列表上方，与触发点分离**
1. 选一个文档较多的知识库。
2. 在文档列表中滚动到中后部，点击某一行的 [删除]。
3. 观察：确认条被写入 `#kbDocMessage`。该元素在 DOM 中的序号为 **55**，而文档列表 `#kbDocs` 为 **64**——确认条在列表**之前**。

> 实测：`确认条 DOM 序号 = 55；文档列表 DOM 序号 = 64`。
> 问题：文档列表越长，从第 N 行触发的确认越需要**向上滚动**才能看到并点击。确认与被确认的对象在视觉上分离，这是一类典型的误操作温床。

**场景 D｜新增文档的结果落在页面最底部**
1. 在「新增文档」填标题与正文，点击 [添加文档]。
2. 观察：`addDocument()` 把新文档 `unshift` 到列表顶部，并把 `selectedDocId` 切到新文档；但「文档预览」是页面最后一个块。

> 实测 DOM 序号：`kbDocs = 64`、`docTitle = 77`、`docContent = 78`、`docPreview = 84`。
> 问题：提交后页面**不滚动**，结果在视口之外。更别扭的是注意力要跨屏跳：新文档出现在列表**顶部**，而它的内容预览在页面**底部**。

**场景 E｜两个一次性表单可同时展开，无互斥、无未保存提示**
1. 打开 [＋ 新建知识库] 并输入内容。
2. 选中一个知识库，点击 [重命名]。
3. 观察：`#kbCreate` 与 `#kbRenameBox` 的 `display` 同时为 `block`；页面文本中检索不到「未保存」字样。

> 实测：`两者同时展开 = true` / `页面出现「未保存」字样 = false`。
> 问题：与专家工作室不一致——那里有明确的 `有未保存的修改` 状态（`expertDraft`）。同属"编辑"，两个页面给出了不同的契约。

**场景 F｜无选中知识库时「新增文档」仍可填写并提交，错误指向另一个区域**
1. 让 `selectedKbId` 为空（例如删光知识库）。
2. 右栏标题显示为「文档」，但标题下的 hint、`#docTitle`、`#docContent`、[添加文档] 仍然完整可交互。
3. 填好内容点击 [添加文档]。
4. 观察：消息区出现「先在左侧选择一个知识库。」

> 实测：`右列标题 = 文档` / `结果消息 = 先在左侧选择一个知识库。`
> 问题：错误提示出现在**右列**，而它指示的操作对象在**左列**。操作位置与提示位置不同区，用户需要跨栏找"左侧"在哪。

**场景 G｜键盘焦点顺序与视觉顺序不一致**
1. 用 Tab 遍历知识库页可聚焦控件。
2. 观察：焦点列序为 `LLLLLRRRR`。

> 实测：`可聚焦控件数 = 8` / `焦点列序 = LLLLLRRR`。
> 问题：视觉上是两栏并排，键盘上却必须串行穿过整个左栏（5 个控件）才能到达右栏。而知识库页的大量操作恰恰是**跨栏**的（左栏选库 → 右栏改文档），最坏路径要 5 次以上 Tab 往返。

### 3.3 信息密度过高

- **20 个控件、6 个标题层级、2 张卡片全部同时可见**，没有任何页签或折叠来分担。对比桌面外壳同样是"复杂页面"，但被 4 个页签切成每页 ≤6 控件。
- **低频表单常驻**：「新增文档」（标题 + 正文 textarea + 按钮 + hint）在整个页面生命周期内始终绘制，即使使用者只是来检索的。实测确认该表单常驻可见。
- **同一信息重复三处**：文档数量出现在 `#kbDocSub`（"…N 篇 · 检索会切分为 chunk…"）、`#docCountHint`（"N 篇文档"）、以及每个知识库列表项的副标题（"N 篇文档 · source"）。
- **空状态与表单重叠**：没有任何知识库时，右栏仍绘制「新增文档」的完整表单，而它的提交必然失败（场景 F）。
- **两种滚动语义挤在一起**：左栏内部既要滚知识库列表、又要滚检索结果，而它们属于不同的工作面。

## 4. 横向评估：其他菜单有没有同类问题

按"单页堆叠"的严重程度分四级：

### 4.1 重度——建议与知识库一并改造

**规则库**（4 卡片 / 11 标题 / 30 控件 / 12 表单控件 / 0 页签 / 2 671 字）
它是全平台**无页签页面中**的极值。页面内并列了四件可分离的事：规则包选择、规则编辑、试算（dry-run）、事实词表（`FACT_VOCABULARY`）。其中"规则编辑"是写入且带修订号（revision）的事务，"试算"是只读，"事实词表"是参考资料。三者同页堆叠，必然出现与场景 A 同构的问题：**选择一个规则包来"只看看现有规则"，会同时驱动编辑面板与试算面板。**
建议页签：`规则包`（列表 + 需要能力）/ `规则`（选中包内的规则编辑）/ `试算`（dry-run）/ `事实词表`。

**专家工作室**（3 卡片 / 10 标题 / 14 控件 / 0 页签 / 1 030 字）
并列了：专家列表、DAG 画布、草稿编辑（含知识库/资料/规则包/ MCP 授权四组选择器）、清单预览（manifest）。其中"草稿编辑"已经具备 `expertDraft` + `有未保存的修改` 的完整状态机，是本平台**最成熟**的编辑契约；问题在于它与"浏览列表"挤在同一层。
建议：`专家`（列表）/ `流程`（DAG + 节点增删）/ `清单`（草稿编辑 + manifest 预览）/ `授权`（知识库 / 资料 / 规则包 / MCP）。

### 4.2 中度——可改可不改，先修具体缺陷

**数据库资料**（2 卡片 / 17 控件 / 0 页签 / 685 字）
控件数不低，但页面语义单一（资料表列表 + 增删改），两卡片的划分本身是合理的。真正的缺陷是"新增/编辑表单"与列表同页平铺，与知识库场景 B / E 同构。
建议：**不动主结构**，把新增/编辑改为抽屉，并给破坏性删除补模态确认。

### 4.3 已被页签缓解——不需要动

**能力目录**（49 控件 → 单页 ≤21）、**桌面外壳**（27 控件 → 单页 ≤6）。
这两页是本次改造的**现成模板**：它们证明了"页签 + 派生页签列表"这套做法在本原型里跑得通，而且页签本身是**状态**（`data-subview`），可以被 `verify-console.js` 断言。

### 4.4 不需要动

**概览**（0 控件，纯指标卡）、**任务**（7 控件，列表 + 时间线）、**SQL 分析室**（10 控件）。
SQL 分析室值得单独说明：它的 10 个控件服务于**同一个任务流**（输入 → 运行 → 浏览结果 → 流水线），是"一个工作面"，不是"几件事被压在一页"。控件数多不等于堆叠——**判据是"这些控件是否属于同一个任务流"**。

### 4.5 小结

存在同类单页堆叠的菜单：**规则库（重度）、专家工作室（重度）、知识库（重度，本篇主题）、数据库资料（中度）**。不存在的：概览、任务、SQL 分析室、能力目录、桌面外壳。
其中知识库**不是最严重的一页**，但它是**结构最清晰、最适合作为第一批改造样板**的一页——因为它的三个工作面边界干净、彼此无耦合，改造风险最低，改完可以作为规则库与专家工作室的模板。

## 5. 方案论证

### 5.1 先立判据（可复用）

不要凭"感觉哪个更好看"选方案。以下六个判据是本次论证的依据，也建议作为后续页面的统一判据：

| 判据 | 二级页面 | 抽屉 | 弹窗（模态） |
|---|---|---|---|
| 内容体量 | 大：多区块、需要滚动 | 中：一个表单或一个详情 | 小：一次确认或一个短表单 |
| 是否需要与主内容**对照** | 不需要（它**替代**主视图） | **需要**（必须保留主内容可见） | 不需要 |
| 是否需要**可寻址/深链** | 需要 → 必须有 | 一般不需要 | 不需要 |
| 是否中断当前任务 | 不中断（它是导航） | 半中断（叠加，可关） | **强中断**（必须先处理） |
| 是否承载**破坏性确认** | 不适用 | 不适用 | **适用** |
| 是否承载**多步组合操作** | 适用 | 仅单步 | 不适用 |

一句话判据：**"这是目的地，还是附着在上下文上的一次动作？"** 是目的地 → 二级页面；是动作 → 抽屉；是必须先处理完才能继续的动作 → 模态。

### 5.2 方案一：二级页面（页签 / 页内子路由）

**适用场景**：页面里存在 2 个以上**平级且各自完整**的工作面，每个工作面都有独立的列表与操作，且使用者会在它们之间往复切换。

**优点**
- **一致性**：平台已有两处先例（能力目录、桌面外壳），采用它不引入新的交互范式。
- **可组合与可深链**：页签是**状态**而非瞬态。补上 URL 状态后（`#knowledge/docs?base=…&doc=…`），"这篇文档"第一次成为一个可以被引用、被通知、被外部链接定位的对象。这是抽屉与弹窗都拿不到的。
- **可回归**：页签切换是可断言的状态变化（`data-subview` / `aria-current`），能直接扩进 `verify-console.js`。抽屉与弹窗是瞬态的，断言成本高、容易漏测。
- **不新增模态负担**：本产品有一条硬规则——每个控件要么改变可见状态、要么说明为什么不能。模态会引入第二套状态机（打开/关闭/焦点陷阱/Esc 语义），页签不会。
- **体量匹配**：文档列表 + 预览 + 新增三者加总的体量超出抽屉的合理承载。

**缺点**
- 多一次点击才能到达"文档"（当前是左选右显，零点击）。
- 若页签切分不当，会把"主从对照"（选库看文档）拆散，反而变难用——**必须把主从关系留在同一个页签内**。
- 需要改动结构，回归面比纯样式改造大。

**改造建议（针对知识库）**
- 页签三个：`知识库` / `文档` / `检索`。
- `知识库` 页签 = 知识库列表 + 行内 [新建]（抽屉）→ 选中一个进入 `文档`。
- `文档` 页签 = **两栏主从**：左为文档列表（选中知识库的），右为文档预览 + [新增文档]（抽屉）。主从对照留在同一页签内，不跨页签。
- `检索` 页签 = 跨库只读查询。作用域写在页签标题或页签内的固定说明上，不再是"某个库卡片里的一个框"。
- 页签本身派生自状态（与能力目录一致：`manageable || count > 0` 的规则换成"该工作面是否有内容"），避免写死后与现实不符。

### 5.3 方案二：抽屉（右侧滑出）

**适用场景**：附着于当前上下文、一次性的、需要主内容保持可见以作对照的动作。

**优点**
- **保留上下文**：这正是场景 D / F 的解药——新增文档时列表仍在视野内，能立刻看到"加到哪去了"；重命名时能看到正在改的是哪一个。
- **零导航成本**：不离开当前页签，适合高频小操作。
- **天然的"未保存"容器**：抽屉的关闭动作可以挂上"有未保存的修改"确认，补齐场景 E 缺失的状态契约，与专家工作室的 `expertDraft` 对齐。
- 实现轻，视觉上不打断。

**缺点**
- **不能承担主导航**：抽屉关掉就没了，"我现在在哪个工作面"这件事失去表达；也拿不到深链。
- **宽度受限**：大文本编辑（文档正文最多 20 000 字符）在抽屉里体验明显差于整页。
- 与模态叠加时层次容易混乱（抽屉上再开模态），需要明确规则。

**改造建议**
- 用抽屉承载**三个一次性事务**：新建知识库、重命名知识库、新增文档。
- 每个抽屉绑定一个"未保存"状态，并在关闭时询问（与专家工作室统一）。
- 抽屉内不再重复绘制所属列表。

### 5.4 方案三：弹窗（模态对话框）

**适用场景**：必须处理完才能继续的一次性事务，尤其是**破坏性**动作——它是唯一能天然满足"显示影响面 + 强制显式确认"的形态。

**优点**
- **强中断**保证确认被看见，正是场景 C 的解药：确认不再是被写入页面某处的消息行，而是覆盖在当前上下文之上、与触发点直接关联。
- 焦点陷阱与 Esc 语义由原生 `<dialog>` 提供，可达性成本低。
- 适合"必须填写才能继续"的短表单（将来若要求删除时输入库名二次确认）。

**缺点**
- **对浏览/编辑类内容完全不适合**：把它们放进弹窗会让人反复开关，且弹窗内滚动与嵌套滚动都是已知的体验坑。
- 弹窗数量一多就变成"弹窗地狱"，且每个弹窗都是一次模态状态切换，难以与页签的状态模型统一。
- 在桌面壳里有一个额外陷阱：**不要**用 Electron 的 `dialog.showMessageBox` 做业务确认（见第 6 节）。

**改造建议**
- 只用两处：**删除知识库**（模态内必须显示"N 篇文档将被一并移除"以及"被哪些已启用专家引用"，把 `askDeleteKnowledgeBase()` 里已有的 409 语义搬进模态正文）、**删除文档**。
- 实现用 renderer 内 `<dialog>` + `showModal()`；**不要**用 `window.confirm`（项目既有约束）。

### 5.5 方案四：维持单页 + 改良

**适用场景**：页面复杂度接近临界、且短期内不具备结构改动的条件时，作为过渡。

**优点**：改动面最小，`verify-console.js` 回归风险最低。
**缺点**：治标。层级缺失与作用域混装这两类问题**不可能**靠折叠与间距解决——折叠只是把平铺变成"需要点开的平铺"。
**改造建议（若采用）**：至少要修掉场景 A（检索改为不静默改写选中项）、场景 C（确认条移到触发点附近）、场景 E（表单互斥 + 未保存提示）。这三条与结构无关，任何方案下都应做。

### 5.6 推荐选择及理由

> **推荐：二级页面做骨架（页签 = 知识库 / 文档 / 检索），抽屉承载一次性事务，模态只承载破坏性确认。三者组合使用，而非三选一。**

理由，按重要性排序：

1. **判据先于偏好。** 按 5.1 的判据逐项套：知识库的业务被切出的三块（库管理 / 文档管理 / 跨库检索）都是**目的地**——各自完整、需要互相切换、且"这篇文档"应当可寻址。凡"目的地"就该是二级页面，而不是抽屉或弹窗。抽屉与模态在这三块上会在"体量""对照""可寻址"三项判据上相继失分。
2. **一致性即收益。** 平台已经用页签解决过一次同构问题（能力目录、桌面外壳），且效果可量化（49 控件 → 单页 ≤21）。知识库是这条规则的例外，把例外收齐比引入第三种主形态更省认知成本。**引入新范式本身是有成本的，只有当旧范式真的不适用时才值得。**
3. **页签是状态，抽屉与弹窗是瞬态。** 这条决定了可测试性与可回归性。本项目的回归网是行为级的（`verify-console.js`），页签切换能直接扩进断言；瞬态形态只能靠截图人工核验，长期必然腐化。同时，补上 URL 状态后，二级页面顺带解决了"全平台无深链"这个既有缺陷，并在 Electron 下换取通知/外部链接可定位到具体文档的能力。
4. **唯一必须用模态的地方是破坏性确认，而不是导航。** 把模态限制在这一处，既拿到了"确认必须显式"的收益，又避免了弹窗地狱。
5. **抽屉解决的是"动作"而不是"结构"。** 它在场景 D / E / F 上收益最大，成本也最低，因此适合作为第一批落地项——**与页签改造可以并行，互不阻塞**。

**反面意见我也要考虑**：改成页签会牺牲当前"左选右显"的零点击效率。缓解办法是**把主从对照留在同一页签内**（`文档` 页签仍是两栏），并且让"知识库"页签里的行点击**直接进入文档页签**，保持一次点击到达。

### 5.7 落地后的目标结构

```text
知识库
├─ page-head   eyebrow / h1 / 一句说明 / 折叠的接口与边界
├─ tabs        [知识库] [文档] [检索]                    ← 由状态派生
├─ 页签：知识库
│    knowledge-list            列表：[名称 · N 篇 · 来源 · 已授权 M]
│    [+ 新建知识库] → 抽屉（含未保存状态）
│    行操作：[重命名] → 抽屉   [删除] → 模态（正文写明受影响文档数与引用它的已启用专家）
├─ 页签：文档        ← 未选中知识库时说明"先在知识库页签选择一个"，而不是画空表单
│    左：文档列表（该库内）  行内 [删除] → 模态
│    右：文档预览（选中的那一篇）
│        [+ 新增文档] → 抽屉（列表保持可见；提交后高亮新行并滚动到它）
└─ 页签：检索
     固定作用域说明（"范围 = 已启用专家被授权的知识库：…"）
     查询框 + 结果列表；点击结果 = 在「文档」页签打开该篇（并明确提示已切换）
```

## 6. Electron 桌面端实现要点

1. **二级页面用 renderer 内路由，不要为每个二级页面开 `BrowserWindow`。**
   多窗口会让"工作空间 / 运行目标 / 操作历史"这些**壳状态**需要跨窗口同步；而操作历史在本产品里是单调追加的（"a tab switch appends nothing"），多窗口会直接破坏这个不变量。建议 `vue-router` 的 hash 或 history 模式，配合主进程的 `setWindowOpenHandler` 拒绝非预期的新窗口。
2. **唯一有理由开独立窗口的是"把这篇文档放到另一块屏幕对照"**——这是可选增强，不属于 IA，也不应成为默认行为。
3. **模态确认用 renderer 内原生 `<dialog>` + `showModal()`**，拿到原生焦点陷阱与 Esc 语义；**不要**用 `window.confirm`（项目既有约束）；**也不要**用 Electron 的 `dialog.showMessageBox` 承载业务确认——那属于 shell/OS 层，会绕过 renderer 的状态与操作历史。shell 的对话框只保留给"选目录"这类真正的 OS 服务。
4. **抽屉在 renderer 内实现**，Electron 侧无特殊要求；注意与模态叠加时的层级规则（模态始终在最上）。
5. **深链换取桌面能力**：二级页面补上 URL 状态后，主进程的 `app.on('open-url')`（macOS）与通知点击（`notification.on('click')`）可以定位到具体文档。这正是"二级页面"相对抽屉/弹窗在桌面端的一个实打实收益。
6. **键盘加速键**：把页签映射到 Electron 原生菜单的加速键（`CmdOrCtrl+1/2/3`）。注意这与"操作历史只记录动作"不冲突——页签切换仍不写历史。
7. **保持 `DesktopPlatform` 契约不变**：本次改造全是 renderer 内的信息架构调整，不触碰 `chooseWorkspace` / `showNotification` / `openExternal` 等壳服务，因此与桌面壳的适配层实现无关。桌面壳已确认使用 Electron（见第 7 节），所以本节列出的 Electron 专属要点都是**有效约束**，不再只是"两种壳下都成立"的写法建议。

本篇初稿把「桌面端采用 Electron」标注为需要确认的前提，因为当时仓库的书面结论是 Tauri 2。**该前提现已确认为决策：桌面壳改用 Electron**，相关文档与原型已同步（见本节末尾的改动清单）。

保留下面这段来源记录，是因为它解释了这次改动的由来：

- `docs/desktop-spec.md` 原第 11 行：`apps/desktop   Tauri 2 desktop shell`。
- 同文件原有专节 **"Why Tauri instead of Electron"**，并附一张决策矩阵，逐项结论均为 Tauri（渲染器、原生边界、本地 Java 后端、体积）。
- 同文件原第 124 行起列出"重新评估 Electron"的**触发条件**（例如出现无 Tauri 替代的关键 Node 原生库、维护 Rust 插件的成本超过收益），当时这些条件均未触发。

- 原型 `docs/prototype/console.html` 的界面文案是「桌面端 · Tauri 2」。

**这不影响本篇的 IA 结论。** 本次评审给出的改造（页签 / 抽屉 / 模态）全部发生在 renderer 内，壳的适配层是 `DesktopPlatform` 契约，因此两种壳下的信息架构解法一致。换壳真正改变的是**能力边界的表达方式**：Tauri 的边界来自 capability 文件（默认窄），Electron 的边界来自 `webPreferences` 与 preload 白名单（默认宽，必须显式收口）。这一点已写进新的 `desktop-spec.md`，原型的面板也按 Electron 的主进程调用点重列。
